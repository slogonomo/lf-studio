# The studio on one GeForce RTX 5090

Design note for [#56](https://github.com/slogonomo/sol-h3-studio/issues/56): the same studio (page, queue, agent API,
CLI) on a workstation with one RTX 5090 (32 GB), using NVIDIA's
[Sol-H3-RTX5090](https://github.com/NVlabs/Sana/tree/sol-engine/models/minimax_h3/Sol-H3-RTX5090) package, without
changing the DGX Spark path. Status: work in progress on branch `5090`. Numbers marked "to measure" are filled in as
they are measured on a workstation with one RTX 5090, 64 GB of RAM and one NVMe disk.

## What NVIDIA ships for the RTX 5090

`models/minimax_h3/Sol-H3-RTX5090` on `sol-engine` (added in `1fb0648`, last changed in `801f040`) is NVIDIA's Spark
package with CPU offload. The models, weights, recipe and numerics are the Spark's; 36 of its 39 runtime files are
byte-identical to Sol-H3-Spark's. What differs:

- H3 (Stage 1) is built in host RAM: the BF16 DiT is loaded to the CPU, the FastH3 LoRA is merged and the 312 attention
  and FFN linears are converted to FP8 one block at a time on the GPU; then the 50 body blocks stay in pageable host
  memory and each forward copies one block at a time to the GPU.
- LTX-2.5 (Stage 2) uses LTX's own block streaming (`OffloadMode.CPU`): every block pinned in host RAM, LoRA fused at
  load, two GPU slots.
- The Qwen prompt encoder is a native process (no Docker) that is loaded for each request and closed before H3 runs.
- Upscaler, adapter, audio encoder and video decoder move to the GPU only for their phase.
- One full warm-up per session; all stages run one after another.

NVIDIA reports 39.8 s from request to MP4 for one 5 s t2va clip after warm-up, on a host with 188 GiB of RAM ("not a
tested minimum"), GPU maximum 21.6 GB sampled every 2 s. FL2VA and Ref2VA are "not GPU-validated" with CPU offload.

## What it needs

Checkpoints are the Spark's (same files and pinned revisions), so a machine that has them can share them
(`SOLH3_CHECKPOINTS`). Sizes from the manifest:

| | t2va | fl2va | ref2va | all three |
|---|---|---|---|---|
| Download | 141.7 GB | 152.1 GB | 148.2 GB | 219.8 GB |

The two INT8 files used only to build the fixed prompt cache (36.9 GB) are not needed when a cache built elsewhere is
reused: the cache builder and its recipe check are byte-identical in both packages. NVIDIA's 5090 cache builder
requires an SM121 GPU, so on a 5090 the cache has to come from a Spark or from a builder change.

Environments (x86_64, no Docker): Stage 1 and Qwen share a Python 3.12 venv (torch 2.12.0+cu130), Stage 2 uses
Python 3.13 (torch 2.13.0+cu132), as in NVIDIA's measurement. Only `ltx-kernels` is compiled. About 15 GB.

Memory, from NVIDIA's code and the numbers Sol-H3-ComfyUI published for the same package on a host capped at 90 GB:

| | Host RAM | GPU |
|---|---|---|
| H3 while loading (whole BF16 DiT in RAM) | 73 GB peak | |
| H3 after FP8 | 29 GB | |
| H3 + LTX loaded | 68-74 GB | |
| A clip (Qwen per request) | | 21.6 GB sampled max |
| Qwen kept loaded on the GPU | | +14.6 GiB |

A 64 GB workstation has about 60 GiB of RAM, of which a desktop leaves roughly 45-50 GiB; the GPU has about 27 GB
free next to a desktop. NVIDIA's default therefore does not fit: both the load peak and the loaded set are above the
RAM. Pinned memory (all of LTX) cannot be swapped.

## What the 5090 backend changes to fit 64 GB

All of these keep the numerics of NVIDIA's recipe; each is checked against an unchanged run (same seed, same draft
latents and MP4 hash where the run is deterministic).

1. **H3 from a prepared snapshot.** NVIDIA's own Stage-1 construction (BF16 load, LoRA merge, AdaLN tables, FP8) runs
   once per task family and its result is saved block by block: FP8 weights and scales, the BF16 gate projections,
   the AdaLN lookup outputs. Later sessions build the model on the meta device and load the snapshot. Load peak about
   the loaded size instead of 73 GB, and 64 GB less to read at every start. To measure.
2. **LTX partly streamed from disk.** The distilled LoRA is fused once (with LTX's own fuse rule, on the GPU, as the
   pinned path does) and saved. A session pins as many blocks as its RAM budget allows and reads the others from the
   NVMe disk with `O_DIRECT` during each update, overlapped with compute. The budget is a setting. To measure: the
   cost per clip at each budget.
3. **Qwen** per request from the NVMe disk (no RAM held between clips), or kept on the GPU if the measured peak
   leaves room. To measure.
4. **Persistent compile caches.** NVIDIA's 5090 code points Stage 2's Inductor and Triton caches into each session's
   new output folder, so LTX is tuned again in every session (Sol-H3-ComfyUI reports about 15 min). The Spark patch's
   persistent caches carry over; Stage 1's Inductor cache moves off `/tmp`, which is often RAM.

## The patch for the 5090

The Spark patch does not apply to Sol-H3-RTX5090: with its paths rewritten, 22 of its 102 hunks are rejected, all
next to NVIDIA's offload changes. The 5090 gets its own patch:

- `patches/sol-h3-studio-rtx5090.patch` against `patches/BASE_COMMIT_RTX5090` (`801f040`, the last commit that touches
  Sol-H3-RTX5090). It carries every change of the Spark patch (portrait, 3-15 s, reshape, static shapes, compile caches,
  autotune fix, Stage-2 audio held fixed, MiniMax prompt tokens, reference videos at the draft canvas, the load-time
  lines) merged with NVIDIA's offload code, plus the memory changes above.
- Spark-only parts stay out or stay inert: the resident Qwen container and its memory planning, overlapped loading
  (it would add the H3 and LTX peaks), `MIMALLOC_PURGE_DELAY` (aarch64 torch only).
- It changes only `Sol-H3-RTX5090` and the one shared Sana module the Spark patch also changes, in its own checkout.
- Its CPU tests: 143 (the Spark patch's 133, NVIDIA's offload test and 9 new offload tests), run by
  `install/10-sana.sh` once the Stage 1 env exists.

Which parts of the Spark patch apply, and how:

| Spark patch section | On the 5090 |
|---|---|
| 1-2 portrait, 3-15 s | yes; the token count in Stage 2 grows with length, VRAM to measure |
| 3-4 Qwen per request over 10 s, overlapped loading, early resident Qwen | no: Qwen is per request already; overlap off |
| 4 deliver-first (the loading pass renders the first clip) | yes |
| 5 `O_DIRECT` loading | yes where weights are read from disk (snapshots, LTX streaming, Qwen) |
| 6 BSA self-check on 8 calls | yes |
| 7-8 persistent compile caches, autotune-cache fix | yes |
| 9 VAEs built on the GPU | yes (fl2va and ref2va) |
| 10 mimalloc purge | no (x86_64 torch has no bundled mimalloc) |
| 11 audio VAE prefetch | yes; to measure against block streaming |
| 12 reference videos at the draft canvas | yes |
| 13 recompile limit, 14 load-timing lines | yes |
| 15 Stage-2 audio held fixed, 16 MiniMax prompt tokens | yes |
| 17 dynamic text length (off by default) | yes |
| 18 reshape, static shapes | yes |

## How the studio picks its backend

`SOLH3_BACKEND=spark|rtx5090` in the settings file (or the environment), `spark` when unset. Any other value is
refused by the launcher, the server and every install script. What it chooses:

| | `spark` (default) | `rtx5090` |
|---|---|---|
| Package in `SOLH3_SANA` | `models/minimax_h3/Sol-H3-Spark` | `models/minimax_h3/Sol-H3-RTX5090` |
| Sana commit, patch | `patches/BASE_COMMIT`, `patches/sol-h3-studio.patch` | `patches/BASE_COMMIT_RTX5090` (`801f040`), `patches/sol-h3-studio-rtx5090.patch` |
| Python for the venvs and NVIDIA's tools | the system's `python3.12` | CPython 3.12.15 and 3.13.16 from uv 0.13.1 (`install/05-python.sh`, under `$SOLH3_HOME`) |
| Stage 1 env (`install/40-stage1.sh`) | as before, fastvideo-kernel built for SM121 | Python 3.12.15, also the native Qwen encoder's: ComfyUI's requirements, comfy-kitchen, comfy-aimdo; no fastvideo-kernel; `install/constraints/stage1-rtx5090-constraints.txt` |
| Stage 2 env (`install/50-stage2.sh`) | Python 3.12, ltx-kernels for SM120/121, offline-context target | Python 3.13.16, ltx-kernels for SM120 (GCC 14 from conda-forge if the system's gcc is newer than 15; kept, since the extensions load its libstdc++ through their RPATH; `FORCE=1` keeps it, `FORCE_TOOLCHAIN=1` replaces it), no offline-context target |
| A Stage 1 or 2 venv without the done marker | built | adopted without installing anything when its `pip freeze` is `install/freeze/stageN-rtx5090-freeze.txt` exactly (one built by hand to this recipe), else built |
| pip's and uv's caches | pip's default, `~/.cache/pip` | `$SOLH3_HOME/cache/pip` and `cache/uv` (`PIP_CACHE_DIR`, `UV_CACHE_DIR`), so a rerun reuses the ~6.3 GB of wheels |
| Weights (`install/20-weights.sh`) | with the offline weights | without them (the cache comes from a Spark) |
| Qwen image (`install/60-qwen-image.sh`) | built | skipped with a message |
| Manifests (`install/70-manifests.sh`) | `--python-qwen` = the patched `qwen_python.sh` | `--python-qwen` = the Stage 1 python; needs the prompt cache first |
| Prompt cache (`install/80-prompt-cache.sh`) | built with NVIDIA's cache builder | taken from a Spark (`SOLH3_PROMPT_CACHE_FROM`), checked with the package's recipe check, else refused |
| Launcher: Docker checks, container cleanup, `SOL_H3_SPARK_QWEN_*` | yes | no |
| Launcher: RAM floor `SOLH3_MIN_FREE_GIB` | 110 GiB | 42 GiB (a 5 s clip ran in a 44 GiB limit, 40.1 GB peak) |
| Launcher: free GPU memory floor `SOLH3_MIN_FREE_VRAM_GIB` (`nvidia-smi` memory.free) | not checked | 26 GiB (a 5 s clip needed 25.5 GB) |
| Server | `/api/state` `"backend": "spark"` | `"backend": "rtx5090"` |
| Page | "on one DGX Spark", the Spark's measured clip times | "on one RTX 5090", a provisional table of clip times, marked as estimates |

Everything else, the server's behaviour included, is the same: the server uses the backend only for `/api/state`
and the page's `sol-h3-backend` meta tag (so the first paint already has the machine's texts). The cold-start
estimate before any measurement stays 4 min on both, since it also sets the warm-up takeover window. The client
(`bin/sol-h3`) says "most of the machine's memory" where it said "about 110 GiB of the Spark's memory".

Detection: `install/00-check.sh` and `install/90-env.sh` read `uname -m` and the GPU name from `nvidia-smi` (aarch64 +
GB10 = spark, x86_64 + RTX 5090 = rtx5090). 00 fails with the value to export when the machine looks like the other
backend; 90 writes `SOLH3_BACKEND` into the settings file (the value the install used, else spark) and refuses when
the machine looks like an RTX 5090 but the value was never set. `bin/env.example` leaves it commented out, so a copy
of it does not set it. The launcher and the server only read it.

The launcher refuses a value that does not match the patched package: `runtime/geometry.py` (added by both patches)
must exist in the backend's package, `runtime/offload.py` (only in NVIDIA's Sol-H3-RTX5090) must exist for rtx5090
and must not for spark, and a checkout patched for the other package is named with the setting that fits it. Pipeline
workers are found by the backend's package path (`WORKER_RE`), so `--kill` and the cleanup at stop reach only that
package's workers.

Updating the 5090 patch needs only a new `patches/sol-h3-studio-rtx5090.patch` (and `patches/BASE_COMMIT_RTX5090` if
the base moves): `install/10-sana.sh` finds the earlier version in the checkout (its applied copy or this repo's
history), reverses it and applies the new one, as on the Spark. New `SOL_H3_*` settings that the patch checks in
`runtime/config.py` would need to be added to the launcher's and server's settings checks, as for the Spark patch.

## Keeping the Spark path unchanged

- `patches/sol-h3-studio.patch` and `patches/BASE_COMMIT` stay byte-for-byte as they are.
- Without `SOLH3_BACKEND` (every existing settings file) the launcher, install scripts and server do exactly what
  they did. Tests check this (`tests/test_backend.py`): the launcher with no backend set (package path, Docker check,
  110 GiB floor, no GPU memory check), the server's state and page (served unchanged), the page's texts, and every
  install script's `--dry-run`, which differs from before only in 00 (one "ok SOLH3_BACKEND=spark" line), 05 (new,
  does nothing) and 90 (`SOLH3_BACKEND=spark` in the written file, `SOLH3_MIN_FREE_VRAM_GIB=0` on the check it runs).
- The 5090 runs from its own Sana checkout at its own commit, so a Spark checkout never moves.
- The studio's existing tests run against the stub as before; two client tests now expect the neutral "most of the
  machine's memory" in place of "about 110 GiB". `tests/test_backend.py` covers the 5090 backend, and
  `tests/test_page.py` checks the page's texts per backend in a browser.
