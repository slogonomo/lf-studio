# The studio on one GeForce RTX 5090

Design note for [#56](https://github.com/slogonomo/lf-studio/issues/56): the same studio (page, queue, agent API,
CLI) on a workstation with one RTX 5090 (32 GB), using NVIDIA's
[Sol-H3-RTX5090](https://github.com/NVlabs/Sana/tree/sol-engine/models/minimax_h3/Sol-H3-RTX5090) package, without
changing the DGX Spark path. Measured on a workstation with one RTX 5090 (32 GB), 64 GB of RAM (60 GiB visible),
one PCIe 5 NVMe disk and a desktop running (about 4.5 GiB of the GPU and 7-10 GiB of RAM in use), driver 615.78.08.

## What NVIDIA ships for the RTX 5090

`models/minimax_h3/Sol-H3-RTX5090` on `sol-engine` (added in `1fb0648`, last changed in `801f040`) is NVIDIA's Spark
package with CPU offload. The models, weights, recipe and numerics are the Spark's; 36 of its 39 runtime files are
byte-identical to Sol-H3-Spark's. What differs:

- H3 (Stage 1) is built in host RAM: the BF16 DiT is loaded to the CPU, the FastH3 LoRA is merged and the 312 attention
  and FFN linears are converted to FP8 one block at a time on the GPU; then the 50 body blocks stay in pageable host
  memory and each forward copies one block at a time to the GPU.
- LTX-2.5 (Stage 2) uses LTX's own block streaming (`OffloadMode.CPU`): every block pinned in host RAM, LoRA fused at
  load, two GPU slots.
- The Qwen prompt encoder is a native process (no Docker) that is loaded for each request and closed before H3 runs.
- Upscaler, adapter, audio encoder and video decoder move to the GPU only for their phase.
- One full warm-up per session; all stages run one after another.

NVIDIA reports 39.8 s from request to MP4 for one 5 s t2va clip after warm-up, on a host with 188 GiB of RAM ("not a
tested minimum"), GPU maximum 21.6 GB sampled every 2 s. FL2VA and Ref2VA are "not GPU-validated" with CPU offload.

## What it needs

Checkpoints are the Spark's (same files and pinned revisions), so a machine that has them can share them
(`LFSTUDIO_CHECKPOINTS`). Sizes from the manifest:

| | t2va | fl2va | ref2va | all three |
|---|---|---|---|---|
| Download | 141.7 GB | 152.1 GB | 148.2 GB | 219.8 GB |

The two INT8 files used only to build the fixed prompt cache (36.9 GB) are not needed when a cache built elsewhere is
reused: the cache builder and its recipe check are byte-identical in both packages. NVIDIA's 5090 cache builder
requires an SM121 GPU, so on a 5090 the cache has to come from a Spark or from a builder change.

Environments (x86_64, no Docker): Stage 1 and Qwen share a Python 3.12 venv (torch 2.12.0+cu130), Stage 2 uses
Python 3.13 (torch 2.13.0+cu132), as in NVIDIA's measurement. Only `ltx-kernels` is compiled. About 15 GB.

Memory, from NVIDIA's code and the numbers Sol-H3-ComfyUI published for the same package on a host capped at 90 GB:

| | Host RAM | GPU |
|---|---|---|
| H3 while loading (whole BF16 DiT in RAM) | 73 GB peak | |
| H3 after FP8 | 29 GB | |
| H3 + LTX loaded | 68-74 GB | |
| A clip (Qwen per request) | | 21.6 GB sampled max |
| Qwen kept loaded on the GPU | | +14.6 GiB |

NVIDIA's flow does not fit 64 GB. Run unchanged under a 44 GiB memory limit (no swap), it was killed 40 s in, still
loading H3, with 43.5 GiB of anonymous memory. LTX's 40 GB of blocks are pinned, so they could never be swapped either.

## What the 5090 patch changes to fit 64 GB

None of these changes the numbers the models compute: they change where weights wait between uses, not what is
computed. Where a check against NVIDIA's own code was possible, it was made and is listed.

| Change | What it does | Effect, measured | Check |
|---|---|---|---|
| H3 built into file-backed pages (`SOL_H3_FILEBACKED_DIR`) | NVIDIA builds H3 in three passes over its 50 blocks (FastVideo's LoRA merge, the AdaLN tables, FP8), each copying a block to the GPU and back into new anonymous memory, so the whole 66 GB BF16 model sits in RAM. The copies now go to shared file mappings on the NVMe disk instead (deleted at once, reclaimable). | load peak 73 GB -> about 5 GiB of anonymous memory while building | same calls, same values; only the storage of the CPU copy differs |
| H3 pinned after it is built (`SOL_H3_STAGE1_PIN`) | one exact `cudaHostRegister` buffer per block (`Tensor.pin_memory()` rounds each tensor up to a power of two) | Stage 1 7.7 s -> 6.5 s per 5 s clip; H3 holds about 21 GiB | same bytes |
| LTX LoRA fused once, blocks partly streamed (`SOL_H3_LTX_BLOCKS`, `SOL_H3_LTX_RESIDENT_BLOCKS`) | the distilled LoRA is fused into a 37 GB block file once (LTX's own loader, key renaming and fuse rule, on the GPU; about a minute, by the first session); a session pins as many blocks as its RAM allows (`auto`: the available RAM, and any cgroup limit, minus `SOL_H3_LTX_RAM_RESERVE_GIB`, 12) and reads the others from the disk with parallel `O_DIRECT` reads, three blocks ahead | 40 GB pinned -> 3-12 GiB; costs about 1 s per 5 s clip (refine 11.2 s with 4 blocks pinned, 10.1 s with 16) | **bit-identical** to NVIDIA's pinned build: blocks 0, 23 and 47 and all 59 non-block weights the model uses, compared with LTX's own `_build_pinned_source` / `_load_non_block_weights` |
| Qwen loaded in large windows (`SOL_H3_QWEN_FAST_LOAD`) | NVIDIA reads the 15.7 GB checkpoint one tensor at a time through one 64 MiB slot; now front to back in 256 MiB `O_DIRECT` windows, 8 threads, copies on a side stream | worker start + load about 5 s | the conditioning payload's SHA-256 equals NVIDIA's loader's |
| CUDA JIT cache 4 GiB (`CUDA_CACHE_MAXSIZE` for the workers) | at the driver's 1 GiB default the three processes evicted each other's JIT-compiled kernels | the first clip after loading lost 9.5 s in Qwen (0.5 s otherwise); session load about 245 s -> 200 s | |
| 4 Inductor compile workers (`TORCHINDUCTOR_COMPILE_THREADS` for Stage 1 and 2) | one worker per CPU thread costs several GB whenever a new shape compiles | a reshape to a new orientation no longer runs out of RAM | |
| Freed memory returned after each operation (`SOL_H3_MALLOC_TRIM`) | `malloc_trim(0)` in every worker | the idle footprint no longer grows about 1 GB per clip | |
| fl2va/ref2va drop the H3 VAE decoder | Stage 1 only encodes keyframes and references; the decoder is 9.7 of the VAE's 10.4 GB (FP32) | Stage 1 in fl2va 35.4 GiB -> 28.5 GiB | encoding uses only the encoder and `quant_conv` |
| H3 snapshots (`SOL_H3_STAGE1_SNAPSHOTS`) | the finished Stage-1 transformer (pinned FP8 blocks, AdaLN tables, the rest) is saved once per mode and restored on later starts instead of built: the same module tree is made on the meta device with the same classes and FastVideo's own FP8 tagging, and the saved bytes are read with `O_DIRECT` into page-locked buffers. Tied to the checkpoint and LoRA files (content markers), the code that builds it (hashes), torch, FastVideo and the GPU; kept next to the checkpoints (20-24 GB each, one per mode: the launcher sets `SOL_H3_STAGE1_SNAPSHOTS_KEEP=1`; the patch alone keeps two) | H3 construction 155 s -> 5 s (t2va), 131 s -> 3.7 s (ref2va) | **checked on the GPU** (`tests/check_stage1_snapshot_gpu.py`): identical module tree and tensors (every byte, dtype, stride, device), page-locked blocks, bit-exact Stage-1 latents, for t2va and ref2va |
| Ref2VA: free the replaced AdaLN projections | NVIDIA's Ref2VA LoRA wrappers form reference cycles, so the 50 AdaLN projections that the lookup replaces stayed alive, and under block offload on the GPU (0.5 GiB each), until the cyclic collector ran | Stage 1's GPU peak while building Ref2VA 27.4 GiB (out of memory next to a desktop) -> 17.6 GiB | the tables are computed before the projections are freed |
| H3 read ahead while it is built (`SOL_H3_STAGE1_READ_AHEAD`) | `madvise(WILLNEED)` on the next block's pages | | |
| fastload `get_tensors()` | safetensors 0.8's `load_file()` calls `get_tensors()`, which fastload did not wrap, so a load to the GPU returned CPU tensors (on the Spark every caller loads to the CPU, so the Spark is not affected) | | |

Kept from NVIDIA's flow: CPU offload, Qwen loaded for each request (resident it would need 14.6 GiB of the GPU, which a
reference clip does not leave), the stages one after another, warm-up per session.

The 5 s text clip, split: Qwen 0.5 s (its worker starts and loads in about 5 s before that), Stage 1 6.5 s, Stage 2
13.9 s (LTX refine 11.2 s, decode and mux 2.7 s). Runs outside the studio with the patched package's `infer.py` gave the same:
27.5-28.9 s per clip in a 44 GiB limit. For comparison, on the DGX Spark the studio's warm 5 s text clip takes about
55 s, and its README lists 133 s for a reference clip with a 5 s video; NVIDIA reports 39.8 s for its 5090 runtime on
a host with 188 GiB of RAM.

launch on the same install; "first time" builds H3 and saves its snapshot:

| Event | First time | With snapshots |
|---|---|---|
| Launch to the first finished clip (5 s text; the loading pass renders it) | 208-257 s | **57 s** |
| Switching to keyframes (fl2va), first clip | 203 s | **62 s** |
| Switching to reference (ref2va), first clip | 242 s | **79 s** |

Memory, whole sessions (all modes, every length, with snapshots): at most 39.6 GiB of the workers' anonymous memory
(the 48 GiB limit held the rest as page cache) and 24.8 GiB of GPU memory next to the desktop (29.2 of the card's
31.8 GiB in use). Per process, in t2va: Stage 1 about 25 GiB (H3 21 GiB of it), Stage 2 about 15 GiB with 7 LTX
blocks pinned, Qwen about 0.6 GiB between clips; in fl2va Stage 1 about 28 GiB. 5 s text clips also ran in a
44 GiB limit (39.1 GiB peak). Disk: checkpoints 220 GB (205 GiB; the two offline-only INT8 files not needed), the
LTX block folder 42 GB (the 37 GB block file and 5 GB of the other weights), one H3 snapshot per mode 24 GB each (ref2va 20 GB),
environments about 15 GB. Building an H3 snapshot (the first start of a mode, and again after a patch update that
changes it) needs about 66 GB of scratch on the same disk for that start. A changed LTX block identity builds a new
folder next to the old one, so up to two (84 GB) are kept.

Not measured: lip sync and picture quality against the Spark (same models, recipe and patch; the outputs differ at
the bit level because Stage 2 tunes its kernels per machine, as on any two machines).

## The patch for the 5090

The Spark patch does not apply to Sol-H3-RTX5090: with its paths rewritten, 22 of its 102 hunks are rejected, all
next to NVIDIA's offload changes. The 5090 gets its own patch:

- `patches/lf-studio-rtx5090.patch` against `patches/BASE_COMMIT_RTX5090` (`801f040`, the last commit that touches
  Sol-H3-RTX5090). It carries every change of the Spark patch (portrait, 3-15 s, reshape, static shapes, compile caches,
  autotune fix, Stage-2 audio held fixed, MiniMax prompt tokens, reference videos at the draft canvas, the load-time
  lines) merged with NVIDIA's offload code, plus the memory changes above.
- Spark-only parts stay out or stay inert: the resident Qwen container and its memory planning, overlapped loading
  (it would add the H3 and LTX peaks), `MIMALLOC_PURGE_DELAY` (aarch64 torch only).
- It changes only `Sol-H3-RTX5090` and the one shared Sana module the Spark patch also changes, in its own checkout.
- Its CPU tests: 201 (the Spark patch's 135, NVIDIA's offload test, 9 offload tests, 40 for the memory changes and 16
  for the settings checks and the self-checking LTX block folder),
  run by `install/10-sana.sh` once the Stage 1 env exists.

Which parts of the Spark patch apply, and how:

| Spark patch section | On the 5090 |
|---|---|
| 1-2 portrait, 3-15 s | yes; the token count in Stage 2 grows with length, VRAM to measure |
| 3-4 Qwen per request over 10 s, overlapped loading, early resident Qwen | no: Qwen is per request already; overlap off |
| 4 deliver-first (the loading pass renders the first clip) | yes |
| 5 `O_DIRECT` loading | yes where weights are read from disk (snapshots, LTX streaming, Qwen) |
| 6 BSA self-check on 8 calls | yes |
| 7-8 persistent compile caches, autotune-cache fix | yes |
| 9 VAEs built on the GPU | yes (fl2va and ref2va) |
| 10 mimalloc purge | no (x86_64 torch has no bundled mimalloc) |
| 11 audio VAE prefetch | yes; to measure against block streaming |
| 12 reference videos at the draft canvas | yes |
| 13 recompile limit, 14 load-timing lines | yes |
| 15 Stage-2 audio held fixed, 16 MiniMax prompt tokens | yes |
| 17 dynamic text length (on by default since 0.4, `SOL_H3_DYNAMIC_TEXT_LENGTH=0` = graphs per prompt length) | yes; checked on the 5090: a new prompt length costs about 1 s in Stage 1 (7.5 s vs 6.5 s for a repeat), and a repeated prompt and seed gives a bit-identical Stage-1 draft |
| 18 reshape, static shapes | yes |

## How the studio picks its backend

`LFSTUDIO_BACKEND=spark|rtx5090` in the settings file (or the environment), `spark` when unset. Any other value is
refused by the launcher, the server and every install script. What it chooses:

| | `spark` (default) | `rtx5090` |
|---|---|---|
| Package in `LFSTUDIO_SANA` | `models/minimax_h3/Sol-H3-Spark` | `models/minimax_h3/Sol-H3-RTX5090` |
| Sana commit, patch | `patches/BASE_COMMIT`, `patches/lf-studio.patch` | `patches/BASE_COMMIT_RTX5090` (`801f040`), `patches/lf-studio-rtx5090.patch` |
| Python for the venvs and NVIDIA's tools | the system's `python3.12` | CPython 3.12.15 and 3.13.16 from uv 0.13.1 (`install/05-python.sh`, under `$LFSTUDIO_HOME`) |
| Stage 1 env (`install/40-stage1.sh`) | as before, fastvideo-kernel built for SM121 | Python 3.12.15, also the native Qwen encoder's: ComfyUI's requirements, comfy-kitchen, comfy-aimdo; no fastvideo-kernel; `install/constraints/stage1-rtx5090-constraints.txt` |
| Stage 2 env (`install/50-stage2.sh`) | Python 3.12, ltx-kernels for SM120/121, offline-context target | Python 3.13.16, ltx-kernels for SM120 (GCC 14 from conda-forge if the system's gcc is newer than 15; kept, since the extensions load its libstdc++ through their RPATH; `FORCE=1` keeps it, `FORCE_TOOLCHAIN=1` replaces it), no offline-context target |
| A Stage 1 or 2 venv without the done marker | built | adopted without installing anything but Pillow 13.0.0 (#69) when its `pip freeze` is `install/freeze/stageN-rtx5090-freeze.txt` exactly (one built by hand to this recipe), else built |
| pip's and uv's caches | pip's default, `~/.cache/pip` | `$LFSTUDIO_HOME/cache/pip` and `cache/uv` (`PIP_CACHE_DIR`, `UV_CACHE_DIR`), so a rerun reuses the ~6.3 GB of wheels |
| Weights (`install/20-weights.sh`) | with the offline weights | without them (the cache comes from a Spark) |
| Qwen image (`install/60-qwen-image.sh`) | built | skipped with a message |
| Manifests (`install/70-manifests.sh`) | `--python-qwen` = the patched `qwen_python.sh` | `--python-qwen` = the Stage 1 python; needs the prompt cache first |
| Prompt cache (`install/80-prompt-cache.sh`) | built with NVIDIA's cache builder | taken from a Spark (`LFSTUDIO_PROMPT_CACHE_FROM`), checked with the package's recipe check, else refused |
| Launcher: Docker checks, container cleanup, `SOL_H3_SPARK_QWEN_*` | yes | no |
| Launcher: RAM floor `LFSTUDIO_MIN_FREE_GIB` | 110 GiB | 42 GiB (every mode ran in a 48 GiB limit; the workers' anonymous memory peaked at 39.6 GiB, 43.3 GiB before the Ref2VA and `malloc_trim` fixes) |
| Launcher: free GPU memory floor `LFSTUDIO_MIN_FREE_VRAM_GIB` (`nvidia-smi` memory.free) | not checked | 25 GiB (every mode needed at most 24.8 GiB) |
| Server | `/api/state` `"backend": "spark"` | `"backend": "rtx5090"` |
| Page | "on one DGX Spark", the Spark's measured clip times | "on one RTX 5090", clip times measured there at 3, 5, 10 and 15 s, other lengths interpolated |

Everything else, the server's behaviour included, is the same: the server uses the backend only for `/api/state`
and the page's `lf-studio-backend` meta tag (so the first paint already has the machine's texts). The cold-start
estimate before any measurement stays 4 min on both, since it also sets the warm-up takeover window. The client
(`bin/lf-cli`) says "most of the machine's memory" where it said "about 110 GiB of the Spark's memory".

Detection: `install/00-check.sh` and `install/90-env.sh` read `uname -m` and the GPU name from `nvidia-smi` (aarch64 +
GB10 = spark, x86_64 + RTX 5090 = rtx5090). 00 fails with the value to export when the machine looks like the other
backend; 90 writes `LFSTUDIO_BACKEND` into the settings file (the value the install used, else spark) and refuses when
the machine looks like an RTX 5090 but the value was never set. `bin/env.example` leaves it commented out, so a copy
of it does not set it. The launcher and the server only read it.

The launcher refuses a value that does not match the patched package: `runtime/geometry.py` (added by both patches)
must exist in the backend's package, `runtime/offload.py` (only in NVIDIA's Sol-H3-RTX5090) must exist for rtx5090
and must not for spark, and a checkout patched for the other package is named with the setting that fits it. Pipeline
workers are found by the backend's package path (`WORKER_RE`), so `--kill` and the cleanup at stop reach only that
package's workers.

Updating the 5090 patch needs only a new `patches/lf-studio-rtx5090.patch` (and `patches/BASE_COMMIT_RTX5090` if
the base moves): `install/10-sana.sh` finds the earlier version in the checkout (its applied copy or this repo's
history), reverses it and applies the new one, as on the Spark. The patch checks its own settings in
`runtime/config.py` (`check_settings()`): the three folders (an absolute path, or 0/off/false/no), the on/off
switches (0/1, off/on, false/true, no/yes in any case) and the numbers. The launcher's `--check` and the server's start
call it, so a bad value stops the studio before a start, not minutes into it. A new setting goes into that function.

A patch update that changes Stage 1's code (`stage1.py`, `offload.py`, `snapshot.py` and the other files a snapshot's
identity hashes) makes each mode build its H3 snapshot once more on its next start (about 220 s, and ~66 GB of
scratch); one that changes the LTX block code builds the block folder again (about a minute).

## Keeping the Spark path unchanged

- `patches/lf-studio.patch` and `patches/BASE_COMMIT` stay byte-for-byte as they are.
- Without `LFSTUDIO_BACKEND` (every existing settings file) the launcher, install scripts and server do exactly what
  they did. Tests check this (`tests/test_backend.py`): the launcher with no backend set (package path, Docker check,
  110 GiB floor, no GPU memory check), the server's state and page (served unchanged), the page's texts, and every
  install script's `--dry-run`, which differs from before only in 00 (one "ok LFSTUDIO_BACKEND=spark" line), 05 (new,
  does nothing) and 90 (`LFSTUDIO_BACKEND=spark` in the written file, `LFSTUDIO_MIN_FREE_VRAM_GIB=0` on the check it
  runs).
- The 5090 runs from its own Sana checkout at its own commit, so a Spark checkout never moves.
- The studio's existing tests run against the stub as before; two client tests now expect the neutral "most of the
  machine's memory" in place of "about 110 GiB". `tests/test_backend.py` covers the 5090 backend, and
  `tests/test_page.py` checks the page's texts per backend in a browser.
